# 酒店全双工任务助理每日上下文 Demo

> 状态：上下文设计稿，不修改现有 Gateway 或工具。
>
> 依据：`hotel-task-management` 原 Skill 的 `SKILL.md`、`references/index.md`、
> `references/create_task.md`，以及人员解析、工作量查询和任务创建脚本。
>
> 示例日期：2026-08-21。员工、岗位、排班和楼层数据均来自该日原 Skill 索引；
> 登录用户姓名必须由真实登录服务返回，本文不根据相似姓名猜测。

## 1. 这份上下文解决什么问题

它不是酒店知识库，也不是完整 SOP。它是给全双工模型的当日运行指示，使模型在很短的
上下文内知道：

1. 当前登录用户是谁；
2. 今天有哪些员工、各自岗位、负责区域和工作时间；
3. 哪些住客需求应当形成任务；
4. 高频任务应该由什么岗位和人员承接；
5. 多人候选时怎样按区域和工作量派发；
6. 哪些关键前置关系不能被省略；
7. 怎样用简洁、自然的工作语言回复。

模型依据这份上下文做判断，任务工具负责读取和写入真实数据。任务是否创建、修改或完成，
只能以工具返回为准。

## 2. 从原 Skill 到语音上下文的取舍

| 原 Skill 内容 | 处理 | 进入每日上下文的形式 |
|---|---|---|
| 登录用户 ID、姓名、酒店 | 保留并补充 | 作为独立身份段，由登录态实时生成 |
| 员工姓名、ID、岗位、排班、楼层 | 完整保留 | 作为团队共享的当日人员索引 |
| 任务生成与不生成的边界 | 保留并压缩 | 4 条判断规则 |
| 上班时间覆盖、岗位匹配、工作量比较 | 完整保留 | 作为有先后顺序的派发规则 |
| 楼层和负责区域 | 保留并强化 | 放在岗位匹配之后、工作量比较之前 |
| 多岗位、多班次协作 | 保留并压缩 | 只保留什么时候需要多执行人 |
| 执行人的逐级监督人 | 保留 | 自动写入 `COLLABORATOR` 的规则 |
| 高频动作的角色、时效、依赖关系 | 保留 | 每个动作压缩为一行决策卡 |
| 完整动作 SOP、话术、敲门距离、清洁步骤 | 舍弃 | 不常驻；需要时另行检索 |
| 低频产品、房型、会议厅、餐厅和权益知识 | 舍弃 | 不参与日常派活，不常驻 |
| `description` 中自动复制多条 SOP | 舍弃 | 只写客户特殊要求、必要约束和交付信息 |
| API 地址、Token、Python 调用方法 | 舍弃 | 属于 Gateway/工具实现，不暴露给语音模型 |
| 最多三次重试等脚本策略 | 舍弃 | 由工具层负责，不让模型自行重试 |
| “无法确定时分给同部门所有员工” | 保留为末级兜底 | 仅在工具支持部门派发且没有唯一人选时使用 |

这里对原逻辑最重要的改动只有一项：删除 SOP 展开，不删除派发判断。也就是说，模型仍然
知道“谁来做、何时做、是否需要协作、先做什么后做什么”，但不背诵每项工作的完整步骤。

## 3. 推荐的每日上下文组成

运行时将三段合并后一次性注入模型：

```text
稳定基础指示（随版本发布，约 500-800 token）
+ 当前登录用户身份（每个用户不同，约 100-250 token）
+ 酒店当日共享上下文（全团队基本相同，约 2,000-3,500 token）
```

建议正常总量控制在 3,000-4,500 token，硬上限 6,000 token。超限时按以下顺序删除：

1. 示例；
2. 非当班员工的详细区域信息；
3. 低频动作；
4. 非派发所需的组织信息。

不得先删除人员 ID、当班时间、负责区域、岗位关系和派发优先级。

3. 工具返回成功前，禁止说“已创建、已派发、已修改、已完成、已通知”。
4. 工具失败时只说失败环节和最短原因，不假装成功，不凭旧结果回答。
5. 不把内部 ID、工具名、接口名、规则来源读给用户；只有用户明确询问技术细节时才解释。
6. 工作场景回复要短。正常成功结果优先用 1 句话；存在异常时最多补 1 句。

【什么时候创建任务】
满足以下条件时创建任务：需求需要立即执行，或有明确的未来执行时间；并且需要员工在当前
对话或现场之外继续执行。纯咨询、系统字段补全、规则核对、费用试算，以及员工能在当前
现场立即闭环的事项，不创建任务。

一个连续需求只创建 1 个任务。洗衣取件和送回等多阶段动作仍为 1 个任务，用多个执行人和
时间约束表达，不拆成重复任务。

任务标题采用“房号/地点 + 动作 + 数量 + 对象”。房号写“房”，数量用阿拉伯数字。
例如：“1601房送2瓶水”“2305房清洁”“1703房查房”。任务描述不复制 SOP，只保留用户
原始要求、特殊注意事项、跨岗位关系和验收所需信息。

立即执行且没有未来开始时间时，状态使用 IN_PROGRESS；有明确未来开始时间时，状态使用
PENDING_RECEIPT。开始时间和完成时间必须按用户原意区分，不得臆造。

【自动派发顺序】
用户明确点名执行人时，优先尊重点名；如果该员工不在本索引、岗位明显不匹配或班次不能
覆盖任务时间，不要偷偷换人，应简短说明冲突并给出可执行人选。

用户未点名时，严格按以下顺序逐级缩小候选范围，后一步只能在前一步留下的人中选择：
1. 时间覆盖：员工班次必须覆盖任务的执行区间；单人无法覆盖时，才安排跨班次协作。
2. 岗位匹配：只保留具备该动作职责的岗位；支持、审批、提供信息的人不算执行人。
3. 区域优先：有房号或楼层时，优先该楼层负责人；全楼层人员只作覆盖或兜底，不抢占专属
   楼层负责人。
4. 工作量均衡：仍有多名候选时，查询候选人的当日未完成任务量，选择数值最小者。查询失败
   时不得把缺失值当成 0；工作量相同则优先专属区域人员，其次选择更少跨楼层移动的人。
5. 末级兜底：仍不能唯一确定时，只有在任务工具支持部门派发的情况下，才派给匹配部门的
   当班人员；否则明确说“暂时无法确定执行人”，不得猜测人员 ID。

多岗位协作时，每个实际到场或完成线下动作的人都列为 EXECUTOR。仅提供审批、监督或线上
核对的人不列为 EXECUTOR。每个执行人的监督链按岗位关系逐级加入 COLLABORATOR，重复人员
只加入一次。

【岗位关系】
- RA 楼层服务员：负责查房、住中清洁、退房清洁、客房送物、开门核验、设施初查、洗衣

- 房务中心经理助理：协助团队管理，直属上级为房务中心经理。

## 5. 每日生成与更新契约

上下文服务按 `hotelId + businessDate` 生成团队共享段，按 `userId` 生成身份段。推荐返回：

```json
{
  "contextId": "hotel-10082-daily",
  "version": "2026-08-21-01",
  "generatedAt": "2026-08-21T06:00:00+08:00",
  "effectiveFrom": "2026-08-21T06:00:00+08:00",
  "expiresAt": "2026-08-22T06:00:00+08:00",
  "subject": {
    "userId": "2079698_hotel_10082",
    "displayName": "<由登录服务返回>",
    "hotelId": "10082"
  },
  "teamContextVersion": "hotel-10082-2026-08-21-01",
  "identityInstructions": "<当前用户身份段>",
  "teamInstructions": "<当日团队共享段>",
  "estimatedTokens": 4200,
  "contentHash": "sha256:<完整上下文哈希>"
}
```

更新规则：

1. 会话建立后先取得可信登录身份，再请求上下文；不得让模型或用户填写 ID。
2. 收到上下文并成功更新会话后，才允许自动派发依赖排班的任务。
3. 新版本发布时替换旧的每日上下文，不追加到旧上下文后面。
4. 身份变化只替换身份段；排班、区域或动作规则变化才替换团队共享段。
5. 已过期且没有新版本时，可以继续查询真实任务，但暂停依赖旧排班的自动选人；用户明确
   点名且工具能验证人员时，可以按点名执行。
6. 每次发布前校验：员工 ID 唯一、班次格式有效、楼层冲突可解释、监督链无循环、总 token
   不超过上限。

## 6. 需要用户确认的两个产品判断

这两个点不是原 Skill 缺失，而是原逻辑在正式产品中的风险边界：

1. **无法唯一选人时是否允许派给同部门所有员工。** 本 Demo 忠实保留为最后兜底，但批量
   派发可能产生重复接单。正式版可改为部门公共队列，前提是任务 API 支持该对象。
2. **用户点名与排班冲突时如何处理。** 本 Demo 不静默换人，而是说明冲突并推荐人选；若
   业务上允许管理者强制点名，可给登录身份增加 `canOverrideSchedule`，不要靠模型猜权限。

## 7. Demo 验收问题

1. “1601房送2瓶水。”应选择刘嘉豪，标题为“1601房送2瓶水”。
2. “2305房打扫一下。”应选择曲俊宇；标准完成时间可按 30 分钟计算。
3. “1703房电视坏了，派人修。”应先形成 RA 排查，不应直接只派工程维修。
4. “1810房查完了，浴室漏水。”应记录查房完成和漏水异常，但不能说房间已可售。
5. “把我的进行中任务报一下。”应使用当前登录用户 ID 查询，不追问 ID。
6. “给施展派一个今晚的客房任务。”应指出施展今日不上班，不得假装已派发。
7. 工具返回“任务成功、通知失败”时，只能回答任务已创建、通知失败。
