# 酒店语音记录工具

## 工具分工

- 尚待执行且需要在对话外继续推进：使用任务工具。
- 已经发生或已经确认、且本轮无需派活：使用 `atomic_record_write`。
- 同一快模型轮次中，任务修改和事件写入互斥。
- 用户要求改正或删除：使用 `atomic_record_correct`，不新增一条冒充修改。

## 写入结构

```json
{
  "category": "物品",
  "factState": "occurred",
  "action": "借出",
  "content": "1015房本次住店已借出充电宝1个",
  "facts": {
    "itemName": "充电宝",
    "quantity": 1,
    "unit": "个"
  },
  "entities": [
    { "type": "room", "id": "1015房" },
    { "type": "stay", "id": "本次住店" }
  ]
}
```

语音快模型工具要求 `category`、`factState`、`action` 和 `content`，其中 `factState` 用来区分“已经发生/已经确认”和“仍待执行”。底层原子空间为慢模型、系统触发和未知事项保留 `category + content` 的通用兜底，但已经定义最低标准的动作不能绕过该标准：例如借出、借用、外借、借给必须有物品、数量，并至少能确定房间、住店记录、客人或员工之一。常见物品单位由 Gateway 根据物品目录补齐。

## 四个类别

- 物品：送出、消耗、借还、售卖、库存结果、拾获、交存。
- 客人：投诉、要求、报失、偏好、住店变化、服务结果。
- 酒店：房间设备、公共区域、交通天气、交接和恢复。
- 其他：任何无法稳定归入前三类的已发生事实。

失物不是独立类别：客人说物品丢失，写客人“报失”；员工捡到物品，写物品“拾获”。不创建失物 ID。

## 内容要求

`content` 必须是脱离当前对话仍能独立理解的稳定事实：

- 不合格：`本次住店期间不安排靠电梯`
- 合格：`张先生2026年8月26日至28日的本次住店，排房时排除靠近电梯的房间`

能准确提取的数量、单位、地点、原因、结果和明确对象写入 `facts/entities`；没有说出的内容不猜。实体未建档或动态实例暂时查不到，不阻断 `content` 落库。

## 错误交互

- 参数错误且用户信息已足够：模型内部修正并只重试一次，不向员工解释。
- 确实缺少会改变业务事实的信息：只问缺少的业务信息，例如“借了几个充电宝？”
- 反问时不创建“待补充记录”；用户补充后再一次性写入完整事件。
- 系统连续失败：只说“这条暂时没有记成，我保留着刚才的内容。”
- 不向员工说字段、类型、代码、ID、接口、校验规则或内部错误。

## 语音回执

写入成功后由 Gateway 复述可核验的事实，不允许只说“已记录”。例如：`已记录：2016房，借出雨伞1把。`

同样规则适用于任务和通知：任务回执必须包含执行人和任务内容；通知回执必须包含接收人和通知内容。

## 盘点

盘点是任务动作。只有盘点后已经核实的数量、消耗或差异，才写物品记录。
