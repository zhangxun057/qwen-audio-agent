# 酒店慢模型事件写入规范

慢模型通常从任务状态、执行记录、PMS 变化或用户明确要求中写事件。它与快模型使用同一个统一事件元模型，但可以花更多时间补齐事实和关联。

## 1. 何时写

- 任务只是创建、开始或流转，没有产生新的业务事实：不写事件。
- 任务结果已经核实了借出、归还、消耗、故障、服务结果等事实：写事件。
- 同一任务状态重复扫描：依靠 `sourceTaskId + sourceTransitionId` 幂等，不重复新增。
- 盘点动作本身不写；盘点后得到的核实数量、消耗或差异才写。

## 2. 统一结构

```json
{
  "category": "物品",
  "action": "归还",
  "content": "1015房本次住店已归还充电宝1个，客房中心验收外观正常",
  "facts": {
    "itemName": "充电宝",
    "quantity": 1,
    "unit": "个",
    "condition": "外观正常"
  },
  "entities": [
    { "type": "room", "id": "room:1015" },
    { "type": "stay", "id": "stay:..." },
    { "type": "item", "id": "item:power-bank" },
    { "type": "task", "id": "task:..." }
  ],
  "sourceTaskId": "task:...",
  "sourceTransitionId": "transition:..."
}
```

只有 `category` 和 `content` 是统一硬要求；慢模型应在有可靠依据时尽量补齐 `action`、`facts` 和 `entities`。

## 3. 类别

- 物品：送出、消耗、借还、售卖、库存核实、库存调整、拾获、交存。
- 客人：投诉、要求、报失、偏好、住店变化、服务结果。
- 酒店：设施异常、故障核实、公共区域变化、交通天气、交接、恢复。
- 其他：无法稳定归类，但事实本身值得保留。

类别不负责表达全部业务含义。具体含义由 `action + content + facts + entities` 共同表达。

## 4. 关联

- 明确提到且彼此独立的对象都可以关联，例如房间、住店记录、物品、员工和来源任务。
- 酒店租户、记录人、记录时间等系统信息由 Gateway 注入，不要求模型重复关联。
- 房号可以直接映射；住店记录、订单等动态对象通过原子空间查询。
- 查不到实例时保留待解析引用，不能因此丢失已经核实的事实。

## 5. 典型结果

### 任务完成：送两瓶水

```json
{
  "category": "物品",
  "action": "送出",
  "content": "2015房本次住店已送入矿泉水2瓶",
  "facts": { "itemName": "矿泉水", "quantity": 2, "unit": "瓶" }
}
```

### 客诉后核实设备故障

客人最初投诉时可以已有一条“客人/投诉”记录。工作人员核实后再写：

```json
{
  "category": "酒店",
  "action": "故障核实",
  "content": "2615房空调已核实为不制冷故障",
  "facts": { "observation": "空调不制冷", "result": "故障已核实" }
}
```

不要把最初投诉覆盖成故障记录；两条事实可以通过房间、住店和来源任务自然关联。

### 盘点结果

```json
{
  "category": "物品",
  "action": "库存核实",
  "content": "客房中心当前可用乳胶枕12个，使用中8个",
  "facts": {
    "itemName": "乳胶枕",
    "availableQuantity": 12,
    "inUseQuantity": 8,
    "unit": "个"
  }
}
```

## 6. 更正

听错房号、数量或事实时，调用更正能力更新原记录，并同步更新 `content`、对应 `facts` 和 `entities`。不要通过新增一条相反记录来隐藏错误。
