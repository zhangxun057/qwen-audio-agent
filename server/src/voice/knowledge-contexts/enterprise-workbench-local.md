## 核心结论

- 工作台采用语音前台、Gateway 调度层、后台 Agent/工具层的分层结构。
- 全双工模型负责低延迟听说；需要实时资料、企业系统读写或复杂执行时，由 Gateway 路由到知识包或后台 Agent。
- 动态知识实验的基础会话只携带短协议；大型知识包通过单次 response instructions 注入，不预先塞进常驻会话。
- 注册包命中后显示“已命中，正在加载知识库”，真正创建携带资料的回答时才显示“知识库已动态注入”。
- 未注册主题不得进入无限等待，应由模型正常回答或调用后台 Agent。

### 浏览器怎么连接 DSH

DSH 当前 WebUI 自己就是这样工作的：

- `POST /api/session.create`：创建会话
- `POST /api/session.prompt`：发送任务
- `GET /api/events.mux`：通过 SSE 接收实时执行过程
- `POST /api/session.cancel`：取消任务
- 其他接口读取历史、模型、工作区和附件

但有一个关键限制：DSH 当前按“同源、本机可信页面”设计。你们部署在云端的网页，不能直接、无保护地调用用户电脑上的 `127.0.0.1`。

因此要增加一个“企业工作台本地连接器”：

```text
云端工作台网页
      ↓ 配对令牌
本地连接器 localhost
      ↓ DshAdapter
DSH API / Cordis 内核
```

本地连接器负责：

- 检测 DSH 是否启动
- 与网页进行一次性安全配对
- 把工作台任务转换为 DSH 会话和 Prompt
- 把 DSH 事件流转成工作台能理解的进度事件
- 限制允许访问的工作目录
- 处理审批、取消和产物回传

### 现有云端绘图怎么兼容

把现有绘图接口封装成一个 DSH Tool 插件，例如：

```text
enterprise_draw
  输入：绘图需求、数据、输出格式、执行方式
  路由：
    cloud  → 调用现有云端绘图 API
    local  → 调用本地 Python/Node/ComfyUI 等
    hybrid → 本地处理敏感数据，云端完成重型渲染
  输出：图片、SVG、HTML 或本地文件路径
```

这样做以后：

- 网页交互不用重写。
- 原有云端绘图继续使用。
- DSH 负责理解需求、规划步骤、调用绘图工具、保存文件和记录轨迹。
- 后续可以逐步增加本地绘图能力。
- 每次绘图调用都会进入 Session Log，可审计、可复盘。

可以。`127.0.0.1` 只代表“网页和服务运行在你这台电脑上”，不代表它不能访问互联网。

核心区别是：

```text
允许：
本地网页 → 本地后端 → 互联网云端 API

不直接允许：
互联网云端 → 127.0.0.1
```

因为云端看到的 `127.0.0.1`，指的是云端服务器自己，不是你的电脑。

对我们这个项目，最合适的端云协同结构是：

```text
DSH WebUI（本地 27880）
        ↓
AI协办 / DSH 本地后端
   ├─ 读取本地文件、软件和内网数据
   ├─ 调用 DeepSeek/OpenAI 等云模型
   ├─ 调用企业云端 API
   └─ 把结果与任务状态返回 WebUI
```

不要让浏览器直接携带 Key 调云端。应当由本地后端代为调用，这样可以解决 Key 泄露、跨域限制、权限控制和审计问题。

如果希望“云端主动把任务交给本地电脑执行”，推荐反过来建立连接：

```text
本地 DSH Agent
      │ 主动建立出站 WebSocket / 轮询
      ▼
云端任务中心
      │ 下发任务
      ▼
本地执行 → 上传结果或摘要
```

这样不需要把本机 `27880/27881` 暴露到公网，安全性更高。云端只负责身份、任务队列与协同；本地负责文件、软件和敏感数据操作。

对「企业智能体工作台」，我建议形成三层：

- 云端：账号、组织、任务中心、公共知识、跨设备状态。
- 本地 DSH：本地文件、桌面软件、内网系统和插件执行。
- 路由层：判断本次任务在哪里执行、哪些数据允许上传。

第一阶段可以先做一个最直观的试验：在当前 AI协办任务中增加一个“云端数据源”，由本地 DSH 拉取云端数据、在本地分析，然后只把结论写回任务卡。界面明确显示：

- 数据来自哪里。
- 哪一步在云端完成。
- 哪一步在本地完成。
- 哪些原始数据没有离开电脑。

这就是最小可用的“端云协同”，比先暴露本地端口更稳，也更容易逐步扩展。

理论上，我创建任务的时候，比如把这个开关打开，那它执行的任务就是：当我的任务创建之后，默认把任务的结构化信息作为上下文，新建一个会话。这就是“AI 协办”的要义了。我们现在做的 AI 协办，应该是任务结构化信息的任何一次改变（比如状态变更），都会触发 AI 做一次思考。我们会把这些信息都丢给 AI，以确保它全程知道任务的变化。至于它如何协办，靠的是 AI 自己的分析推理能力和它预装的一些 skill。这里我们不过多展开，就用它原生的能力。好，这就是我心目中的自动化 AI 协办。

如果我关闭这个开关也没有问题。每个任务也应该有一系列关联的会话，如果没有可以新建。比如我新建一个会话，它依然会把上下文带进去，只是说这个输入是由我主动发起的，区别仅此。
你看一下 V9 版本有没有设计“关联绘画”的概念，我理解之前是有的。理论上，如果我们把它在 DSH 的框架下做通，就可以让绘画和任务真正关联在一起。

我们预选一个最简单的逻辑：
1. 如果有“AI 自动协办”开关：
它一定会有一个初始的关联绘画。也就是在第一次新建任务时，把任务塞进去执行的那个绘画，是任务创建之后自动发起的。

2. 如果没有这个开关：
绘画区域大概是空的。我会选择“新建”，新建完成之后，在和它对话时，这个绘画就会和任务绑定。再次进来时，它就不再是新建状态了，那个地方就会有历史记录可以关联。

另外，因为我们现在支持多绘画，所以还可以新建别的绘画。

小结一下，我们的目标就是把任务看板和 DSH 真正拉通：

1. 自动发起会话：在支持任务新建且自动协办的情况下，要在任务创建的那一刻，自动给我发起一个带入上下文、请 AI 协助执行的会话。
2. 关联会话跳转：在任务列表和任务详情页中，应该能看到该关联会话并跳转进去。跳转的效果与在侧边栏点击会话没有区别。

### 会话技术摘录
角色：助手
你判断得准：现在真正接通 DSH 的只有 5 个预设任务，自定义任务仍停留在前端，所以才没有自动协办和关联会话。接下来我会把“任务”改成后端实体：所有新建任务都可开关自动协办、自动携带结构化上下文创建 DSH 会话，并在列表和详情中展示全部关联会话。

### 会话技术摘录
角色：助手
后端实体层已经补上。接下来我会用你刚才的 “Whatever” 做真实验收：创建在“执行中”、默认开启自动协办，并检查它是否立刻获得 DSH Session、是否真的把任务上下文发给模型。
